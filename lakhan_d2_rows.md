## 3. Design decisions

| Decision | Alternative rejected | Reason | Trade-off |
|---|---|---|---|
| Links must be https | Allowing http and other schemes | It presents the security problem of unsafe links that can exploit system or application logical bugs (custom url schemes are usually avoided), also to avoid linking to unsafe sites. | All linked sites must be secure else they can't be linked. |
| Queries with no results always return status 200 | Erroring with something like 404 Not Found | It's better from a system design perspective to reserve error status codes for real problems while serving a request. A query with no results isn't a failure. Also, 404 means the resource named in the URL doesn't exist, but `/games` does exist; it just found nothing. | Clients must read the JSON response to check the empty items array. |
| Content can only be created and deleted | Allowing a PATCH request to edit content | This can allow for content to be edited to be misleading after someone uses the resource. For example, someone's account could be taken over and links in their UGC could be replaced with malware links. | People cannot "fix" the content of posts after creation. |
| Query can be partial match | Exact match only | A user may not know the exact marketing name of a given game or other entity in the database. | Substring searches are slow on large catalogues, results are less relevant. |

## 4. Assumptions

1. The catalogue is meant to be publicly accessible for unauthenticated users.
   - People randomly browsing the site shouldn't need to sign up and authenticate to browse.
1. Genres in the database are maintainer-set, not automatically catalogued based on games in the database.
   - Application business logic becomes simpler to maintain.
1. Results come back in fixed-order every time, pagination can remain stateless.
   - Pagination of the same query is deterministic, always returning the same values.
