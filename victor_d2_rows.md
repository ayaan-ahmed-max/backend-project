**Conventions used in the examples**
- Requests marked "Token" send the header `Authorization: Bearer <token>`, using the token returned by login.
- Seed data used in the examples (Victor owns the seed, so these are the proposed fixed values):
  - User 1 (`mod_alex`) is the seeded **maintainer**.
  - User 2 (`mira_plays`) and user 7 (`pixelknight`) are players, matching Task 1's examples.
  - Game 3 (`Hades`) is a seeded game.
  - Thread 12 on game 3 was started by user 7. Post 40 is its first post, by user 7; post 41 is a reply by user 2.
  - Ids 99999 do not exist.
- Sad inputs and sad outputs are numbered so that each input lines up with its output. Each one becomes a Bruno request with the same name.
- Sad paths follow the plan's order of checks: 401, then 400, then 422, then 404, then 403, then 409.
- "Empty" means the text is missing all visible characters: `""` and `"   "` are both empty. The API trims leading and trailing spaces before checking lengths.

| FR | Table | Columns (type) | Keys and relationships | Constraints |
|---|---|---|---|---|
| FR11 | threads | id (INTEGER)<br>game_id (INTEGER)<br>user_id (INTEGER)<br>title (VARCHAR(200))<br>created_at (DATETIME) | PK: id<br>FK: game_id references games.id ON DELETE RESTRICT<br>FK: user_id references users.id (default RESTRICT; users are never deleted through the API, fix F7)<br>One to many: a game has many threads; a user starts many threads.<br>One to many: a thread has many posts (posts.thread_id). | game_id NOT NULL<br>user_id NOT NULL<br>title NOT NULL<br>CHECK (length(trim(title)) >= 1)<br>CHECK (length(title) <= 200)<br>created_at NOT NULL DEFAULT CURRENT_TIMESTAMP<br>ON DELETE RESTRICT on game_id: a game with forum threads can't be deleted (the API returns 409), so players' discussions are protected like the rest of their data.<br>Index on game_id, for `GET /games/{id}/threads`. |
| FR11 | posts | id (INTEGER)<br>thread_id (INTEGER)<br>user_id (INTEGER)<br>body (VARCHAR(5000))<br>created_at (DATETIME)<br>updated_at (DATETIME) | PK: id<br>FK: thread_id references threads.id ON DELETE CASCADE (fix F13)<br>FK: user_id references users.id (default RESTRICT, fix F7)<br>One to many: a thread has many posts; a user writes many posts. | thread_id NOT NULL<br>user_id NOT NULL<br>body NOT NULL<br>CHECK (length(trim(body)) >= 1), so an empty post is refused by the database too<br>CHECK (length(body) <= 5000)<br>created_at and updated_at NOT NULL DEFAULT CURRENT_TIMESTAMP. **Fix F11:** SQLite does not enforce VARCHAR lengths, so both length limits (title 200, body 5000) have a CHECK as well as the API's 422.
**Fix F12:** neither table has a role, status or type column, so no extra NOT NULL is needed. Every column is NOT NULL apart from the primary keys, which SQLite fills in.
**For Haarisah's index list (fix F5):** please add `threads(game_id)` and `posts(thread_id)`. Both are foreign keys that the list endpoints filter on.

## 3. Design decisions

| # | Decision | Alternative rejected | Reason | Trade-off |
|---|---|---|---|---|
| 1 (fix F13, agreed with Haarisah) | `posts.thread_id` is ON DELETE CASCADE. The API decides who can delete: a maintainer can delete any thread; an author only while no other player has replied (otherwise 409). | ON DELETE RESTRICT, where a thread can't be deleted while it has posts | A thread always has at least its first post, so RESTRICT would make every thread undeletable unless each post were deleted first, one request at a time. That defeats fix F4, which exists so maintainers can remove bad content. Posts have no meaning without their thread, unlike reviews and collections, which still make sense without the game (and so use RESTRICT). The 409 rule keeps the "players can't damage other players' data" principle: an author can't wipe out replies. | A maintainer's delete removes other players' replies too. That is intended for moderation, and the Bruno test checks that the posts are gone. |
| 2 (own decision) | Creating a thread also creates its first post: `POST /games/{id}/threads` takes `title` and `body` and saves both in one transaction. | A thread with only a title, and the opening text added with a separate `POST /threads/{id}/posts` | No empty threads can exist, even if the second request fails or is never sent. The client makes one request instead of two. The opening text is a normal post, so it can be edited and listed like any other post, and threads need no body column. | If the author deletes the first post, the thread keeps its title but loses its opening text. We accept this because authors control their own posts. |

## 4. Assumptions

1. **Thread titles can't be edited.** There is no `PATCH /threads/{id}`. A title that misleads other readers after replies have arrived would be confusing, and the plan's endpoint list has none. The author can still edit the first post.
2. **Maintainers can delete posts and threads but can't edit them.** Editing would put words in someone else's mouth, and deleting is enough to remove bad content.
3. **Any logged-in user can post, maintainers included.**
4. **Threads are listed newest first; posts are listed oldest first.** New discussions are easiest to find, and a conversation reads in order.
5. **Posts are limited to 5000 characters.** That is long enough for a detailed answer but stops very large bodies. Reviews use 2000.
6. **Text is trimmed before it is checked,** so a body of only spaces counts as empty (422).
7. **Authors always control their own posts.** The author of a post can edit or delete it at any time, with no exceptions. Deleting a post never deletes its thread.
