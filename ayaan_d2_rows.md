**Conventions used in the examples**
- Requests marked "Token" send the header `Authorization: Bearer <token>`, using the token returned by login.
- User 7 (`pixelknight`) is the player registered in the happy path. User 2 (`mira_plays`, `mira@example.com`) is an existing seeded player. Game 3 is an existing seeded game. Ids 99999 do not exist. The names and titles are placeholders until Victor's seed data is agreed.
- Sad inputs and sad outputs are numbered so that each input lines up with its output. Each one becomes a Bruno request with the same name.
- Sad paths follow the plan's order of checks: 401, then 400, then 422, then 404, then 403, then 409.

| FR | Table | Columns (type) | Keys and relationships | Constraints |

| FR9 (also FR8, NFR1) | users | id (INTEGER)<br>username (VARCHAR(30))<br>email (VARCHAR(254))<br>password_hash (VARCHAR(255))<br>role (VARCHAR(10))<br>bio (VARCHAR(500))<br>created_at (DATETIME) | PK: id<br>No foreign keys of its own.<br>One to many: referenced by user_id (or equivalent) in favourite_games, collection_entries, reviews, friendships, follows, threads, posts, user_content and catalogue_changes.<br>Many to many with games through favourite_games. | username UNIQUE NOT NULL<br>email UNIQUE NOT NULL<br>password_hash NOT NULL (hash only, never the readable password)<br>role CHECK (role IN ('player', 'maintainer')) NOT NULL DEFAULT 'player'<br>created_at NOT NULL DEFAULT CURRENT_TIMESTAMP<br>bio optional (NULL allowed)<br>CHECK (length(username) BETWEEN 1 AND 30)<br>CHECK (length(email) <= 254)<br>CHECK (bio IS NULL OR length(bio) <= 500) |
| FR9 | favourite_games | user_id (INTEGER)<br>game_id (INTEGER) | PK: (user_id, game_id), composite<br>FK: user_id references users.id<br>FK: game_id references games.id ON DELETE RESTRICT<br>Link table for the many to many relationship between users and games. | The composite PK stops the same game being favourited twice by one user.<br>Both columns NOT NULL (as part of the PK).<br>ON DELETE RESTRICT on game_id: a game that is someone's favourite can't be deleted (the API returns 409). |

Note on the users table: SQLite treats VARCHAR(n) as a label only and does not enforce the length, so the length CHECKs above make the database enforce the limits as well as the API's 422.

## 3. Design decisions

| Decision | Alternative rejected | Reason | Trade-off |
|---|---|---|---|
| Login uses a token (JWT) that the client sends with every request | Server-side sessions, where the server keeps a record of who is logged in | Bruno, our client, can attach the token to every request, so testing is simple, and the server stores nothing about logins | A token can't be cancelled before it expires, so tokens expire after 1 hour |
| The ownership check is a function called inside each route | A decorator that runs before the route | The owner of a review or post is only known once the record has been found, and the agreed order of checks puts 404 (not found) before 403 (not yours). A decorator would run too early and break that order | Each route must remember to call the check; a missing call would be caught by the 403 Bruno tests |
| An unknown email at login gives 401 with the same message as a wrong password | 404 "user not found" | A different response would reveal which emails are registered, which helps an attacker | A user who mistypes their email gets a less specific message |
| Any field an endpoint doesn't accept gives 400, but a role field on PATCH /users/{id} gives 403 | Silently ignoring unknown fields, or 422 for all of them | Ignoring fields hides client bugs. An unexpected field is a badly formed request (400), while a logged-in user trying to change their own role is a permission problem (403). One rule for every slice means the same mistake gets the same answer everywhere | Clients must send only the fields each endpoint accepts |

## 4. Assumptions

1. **Tokens expire after 1 hour.** A request with an expired token gets 401 and the user logs in again. A short lifetime limits the damage if a token is stolen.
2. **Logout happens on the client, with no logout endpoint.** The client discards the token. A JWT is not stored on the server, so there is nothing for a logout endpoint to delete.
3. **Users log in with their email and password.** The email is unique and is collected at registration, while the username can be changed through the profile.
4. **An unknown email at login gives 401, with the same message as a wrong password.** This stops the API revealing which emails are registered.
